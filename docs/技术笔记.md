# 技术笔记

开发过程中踩过的坑，以及为什么这样修。改这个专案之前建议先读一遍 —— 有几条是违反直觉的。

---

## 1. 签名绑定请求参数与端点，不能自行重放请求

AIHelp 的网关注入 `sign` / `nonce` / `timestamp` 等标头。实测结论：

| 情况 | 结果 |
|---|---|
| 原样重放（不改任何东西） | `200` ✅ |
| 只改 `gameIdList` | `403` ❌ |
| 用统计端点的标头去打客诉列表 | `403` ❌ |

**签名与「原样请求」以及「端点」绑定**。所以「拦截一次请求、之后改参数重放」这条路走不通
（开发初期曾误以为可行，因为改的刚好是同一个值，偶然成功）。

**正确做法：驱动页面自己发请求。**

设定页面元件的状态，然后呼叫它自己的方法，让页面自己产生签名：

```js
// 设定搜寻条件到页面的元件上
nc._data.lastSearchParams = params;
nc._data.lastSearchParamsToSearch = JSON.parse(JSON.stringify(params));
// 呼叫页面自己的搜寻方法 —— 签名由它产生
if (typeof nc.homeSearch === 'function') nc.homeSearch();
```

统计页同理，设定 `SearchView` / `AiDatePicker` 的 data 后点「搜索」按钮。

### 附带收获

客诉列表页的「所有应用」查询**一次就回传全公司所有游戏的客诉**，不需要逐游戏切换。
这一项让整体耗时从 8 分 48 秒降到约 2.5 分钟，而且 403 完全消失。

## 2. 背景分页的 `innerText` 一律是空字串

即使 DOM 完整渲染、`readyState === 'complete'`，非前景分页的 `document.body.innerText` 仍然回传空字串。

开发时曾被这个误导很久：诊断脚本显示「页面是空的、零个按钮」，
但实际上 `body.innerHTML` 有 51 万字节、`.el-tabs__item` 有 8 个。

**判断页面是否载入完成，只能用 DOM 元素数量：**

```js
// ❌ 错：背景分页永远拿到空字串
document.body.innerText.length > 0

// ✅ 对：数元素
document.querySelectorAll('.el-tabs__item').length >= 5
```

同样的坑也出现在登入判断上：不能只看 `innerText` 找「登录您的账号」，
要一并检查 `location.href` 与 `localStorage.getItem('token')`。

## 3. 注入的 XHR 拦截器会残留

一旦用 `Runtime.evaluate` 把拦截器注入页面，**重新载入也清不掉**，
而且每次执行都会再叠一层。叠几层之后页面的 Vue 元件树会坏掉，
症状是「按了搜索完全没反应」。

**做法：每次执行都开全新分页，跑完关掉。**

```js
const created = await conn.send('Target.createTarget', { url: cfg.dashboardUrl });
// ... 采集 ...
await conn.send('Target.closeTarget', { targetId: created.targetId }); // finally
```

另外，每次 `Page.navigate` 之后都要**重新安装拦截器**（换页会清掉）。

## 4. `.vbs` 必须是 UTF-16LE + BOM

Windows Script Host 用**系统 ANSI 字码页**读 `.vbs`：

| 编码 | 结果 |
|---|---|
| UTF-8（无 BOM） | 中文全形标点（`，` `。` `「」`）被拆成无效位元组 → **编译错误**「无效字符」/「未结束的字符串常量」 |
| UTF-8（有 BOM） | BOM 让 `Option Explicit` 解析失败 → **编译错误** |
| **UTF-16LE + BOM** | ✅ 中文、全形标点、引号全部正常 |

改完 `.vbs` 一定要：

```bash
node tools/vbs-to-utf16.mjs bin/launch-hidden.vbs
```

> 补充：`.ps1` 相反 —— 要 **UTF-8 with BOM**，因为 PowerShell 5.1 读 UTF-8 无 BOM 的中文会乱码。

---

## 5. `.cmd` 必须是 CRLF + 纯 ASCII

- **LF 换行**：`cmd.exe` 解析 LF-only 的批次档会出错，双击直接闪退。
- **非 ASCII**：`chcp 65001` 下 `echo` 中文会被解析错，产生
  `'xxx' is not recognized as an internal or external command`。

**做法**：`.cmd` 保持纯 ASCII，中文讯息交给 Node 用 UTF-8 印出来
（`bin/gui.mjs` 的 `--banner` / `--already` / `--failed` 等辅助模式就是为此存在）。

## 6. `.ico` 的小尺寸不能用 PNG 内嵌

GDI+（`System.Drawing.Icon.ToBitmap`）**无法处理 PNG 压缩的 ICO 项目**，
会丢「请求的范围扩展超过了数组的结尾」。

对照实验：

| 格式 | 载入 | ToBitmap |
|---|---|---|
| 全部 PNG 内嵌 | ✅ | ❌ |
| 全部 BMP/DIB | ✅ | ✅ |
| 混合（256 用 PNG，其余 DIB） | ✅ | ✅ |

**做法**：256×256 用 PNG（体积小，Windows 壳层支援），其余尺寸一律 BMP/DIB。
`tools/make-icon.mjs` 已处理。这也是一般 ICO 的惯例做法。

## 7. 隐藏视窗要用 VBS，不能用 `-WindowStyle Hidden`

`powershell -WindowStyle Hidden` 与 `cmd /c start /min` **都会先闪一下视窗**才隐藏。

`wscript.exe` 是 Windows 的 **GUI 子系统程序**，启动时根本不配置主控台；
再用 `Run(cmd, 0, false)`（windowStyle `0` = 隐藏）启动 node —— 全程不会有视窗。

```
wscript.exe（本身无主控台）
   └─ Run("node ...", 0, false)   ← 隐藏
```

---

## 8. GUI 与采集在同一个程序内 → 必须「打不死」

`bin/gui.mjs` 同时是 HTTP 伺服器**和**采集流程的执行者。
任何未捕捉的例外都会让整个介面死掉，使用者看到的症状是「按了没反应」
（浏览器还留着旧画面，所以看起来像介面坏掉）。

已加拦截：

```js
process.on('uncaughtException', handler);
process.on('unhandledRejection', handler);
```

并把错误显示在介面上（红色横幅 + 结果区的错误文字）。

## 9. Node 的 stdout 接管道会缓冲

早期架构是 GUI `spawn` 一个采集子程序。
子程序明明在跑，GUI 却一行进度都收不到 —— 因为 **Node 的 `process.stdout` 在接管道时是缓冲的**，
要等程序结束才一次吐出。

先改成「进度走 stderr」（不缓冲），但子程序架构本身仍然脆弱
（退出码 `4294967295`、路径解析问题）。

**最终解法：完全废掉子程序**，把采集改成可呼叫的模组（`lib/collectCore.mjs`），
GUI 在同程序内直接 `await collect({ onProgress, onLog })`。

`bin/run-weekly.mjs` 也走过同样的路（原本 `spawnSync` 三个 CLI 包装），现已全部改为直接呼叫模组。

## 10. 连接埠被占用要友善处理

没有 `server.on('error')` 时，第二个实例会以未捕捉例外崩溃。

```js
server.on('error', (e) => {
  if (e.code === 'EADDRINUSE') {
    console.error(`端口 ${PORT} 已被占用…`);
    process.exit(1);
  }
});
```

启动器也会先探测连接埠：已在执行就直接开浏览器，不重复启动。

## 11. `new URL()` 会把 host 转小写

判断「使用者是否已完成设定」时，拿 `new URL(cfg.dashboardUrl).host` 与范本值比对：

```
范本值        YOUR-COMPANY.aihelp.net
new URL() 后  your-company.aihelp.net   ← 不相等，判断失效
```

**做法**：比对前统一 `.toLowerCase()`。

## 12. AIHelp 前端的元件名称是选择器的一部分

采集靠操作 Vue 元件达成，所以这些名称是硬依赖：

| 元件 / 选择器 | 用途 |
|---|---|
| `SearchView` | 统计页：设定日期与应用、触发搜索 |
| `AiDatePicker` | 统计页：日期区间 |
| `NewChats` | 客诉列表页：`lastSearchParams` / `homeSearch()` |
| `.el-tabs__item` | 判断页面是否渲染完成 |

如果 AIHelp 大改版，这些是最先要检查的地方。

## 13. 「一级标签加总」不等于真实客诉数

同一笔客诉可能带多个一级标签，所以统计页的 `Sum` 可能大于或小于真实客诉数。
实测案例：某游戏真实客诉 35 笔，一级标签加总 30。

**所以有效／无效一律以客诉列表页的逐笔标签为准**，统计页只用来填报表版面。
`lib/report.mjs` 会在两者差距过大时发出警告。

## 14. 客诉带的是「叶节点」标签，统计页汇总到二级

做「具体内容」摘要时踩的坑：想用客诉的 `tagList` 直接去对统计页的二级标签名，
结果只有约一半能对上。

原因：**标签是树状的，客诉只带最末端的标签。**

举例（DOE 2026-10-02~10-08）：

| 统计页 L2 | 笔数 | 客诉 `tagList` 里的实际值 |
|---|---|---|
| 內容/玩法咨詢 | 13 | 8 笔是 L3「游戏道具」、1 笔 L3「未来咨讯」、4 笔直接标 L2 |
| 异常反馈 | 2 | 1 笔 L3「性能优化」、1 笔 L3「系统界面」 |

所以必须先用**标签树**（`tagLevel2ByGame[gid].tagTree`）把每个叶节点往上捲到它的
L2 祖先，再用 L2 名称分组。这样对出来的笔数与统计页**完全一致**（13=13、2=2、4=4）。

```js
// 从标签树建立 tagName -> { l1, l2 } 对照
walk(tree, []);  // 递归时记录路径上的 level 1 / level 2
// 客诉的每个标签往上捲到 L2，同一个 L2 只算一次
```

## 15. 签章绑定 query 参数，抓对话也不能自己组请求

客诉对话的 API 是：

```
GET /console/api/chat/message/page?ticketId=...&requestGameId=...&limit=100&scrollingDirection=up
```

实测：**原样重放 200，只改 `ticketId` 就 403**。和客诉列表 API 一样，
签章把 query 参数也算进去了。

**正确做法**：呼叫页面元件上的 API 方法，让 axios 拦截器自己产生签章：

```js
const nc = findComponent('NewChats');   // 客诉列表页的元件
await nc.$api.chat.queryMessagePagination({
  ticketId, requestGameId: gameId, limit: 100, scrollingDirection: 'up'
});
```

`$api` 是挂在 Vue 元件实体上的 axios 包装，所有 `/console/api/*` 方法都能这样呼叫。
这比「逐一点击客诉再拦截请求」快得多（95 笔约 1 分钟，且不用滚动虚拟列表）。

回应结构：`data.contentList[]`，每则有 `message`、`customerType`（**3 = 玩家、0 = 客服**）、
`timeStamp`。

## 16. 摘要送模型的资料要放宽长度限制

一开始把「少于 4 个字」的玩家讯息过滤掉，结果「账号找回」这类标签的讯息
全是「帳號」「계정」这种短句，被滤光后整栏变空白。

**做法**：先按正常规则过滤，如果全部被滤掉就放宽到「只要非空」。
宁可送短句给模型，也不要让整栏空白。

## 17. 推理模型的 max_tokens 要给很大，而且会截断「不完整的内容」

`deepseek-flash`、`deepseek-v4-pro` 都是**推理模型**：回应里有
`message.reasoning_content`（思考过程）和 `message.content`（答案），
**思考过程也算 max_tokens**。

踩过的两个坑：

**坑 1：答案完全是空的**

测试连线只给 `max_tokens: 16`，模型把 16 个 token 全花在思考上，
`content` 是空字串、`finish_reason` 是 `"length"`。
→ 测试连线改成 `1024`。

**坑 2：答案「有值但不完整」**

摘要任务给 `max_tokens: 4096`，7 个标签里只回 6 个 ——
因为模型回传的 JSON 被截断了，`content` **有值**，但写到一半就断掉。
只检查「content 是否为空」会漏掉这种情况。
→ **只要 `finish_reason === "length"` 就一律当成需要重试**，
不管 content 有没有值。

**做法**：`lib/llm.mjs` 内建自动加倍重试：

```js
if (finish === 'length') {
  const err = new Error(...);
  err.code = 'TRUNCATED';
  err.reasoningLen = reasoning?.length || 0;
  throw err;   // chat() 外层捕获后把 max_tokens 翻倍重试
}
```

`chat()` 外层最多重试 2 次，每次翻倍（上限 32000），
并用 `reasoningLen * 3` 估一个够用的下限。

**实测对比**（同一批 DOE 7 个标签，2026-10-02~10-08）：

| 模型 | 基本回应 | 摘要耗时 | 结果 |
|---|---|---|---|
| `deepseek-flash` | 0.7 秒 | 3.9 秒 | 一次成功 |
| `deepseek-v4-pro` | 2.4 秒 | 184 秒 | 首轮缺 1 个，重试后补齐 |

结论：**摘要这类归纳任务用小的推理模型就够**，大模型慢 47 倍但质量差不多。

## 18. 模型名称不要写死

一开始我在 UI 里写死 `deepseek-chat` / `deepseek-reasoner`，
结果使用者的帐号实际只有 `deepseek-flash` 和 `deepseek-v4-pro` —— 名称早就改版了。

**做法**：向服务端 `GET {base}/models` 查，把结果列成一排按钮让使用者点选。
这也是 OpenAI 相容 API 的标准端点，各家都支援。

```js
const url = base.replace(/\/chat\/completions$/i, '') + '/models';
// → { data: [{ id: 'deepseek-flash' }, { id: 'deepseek-v4-pro' }] }
```

自动挑选时优先选名字带 `flash|mini|lite|fast|turbo|small|chat` 的（便宜的）。
